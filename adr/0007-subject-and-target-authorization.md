# ADR-0007 主体与目标判定的唯一入口与装配边界

- 状态：`proposed`（内容待项目负责人签署；本 ADR 不改任何代码路径）
- 日期：2026-11-22
- 决策者：待签（建议人：架构评审）
- 关联：V2.9.9 技术规格 §8.1；产品方案 §34.14 / §34.15；`openspec/changes/p8-delivery-tracking`
- 取代：无

## 场景

§11 的两条硬要求是「读取按授权目标返回」「对调用者不可见的客户不出现在 targets 里」，
`delivery_api` 六条路由的 `note` 都写着「§34.12 的主体与目标判定未实现」，拒绝码统一
`BOD_API_DENIED`。

但仓库盘点结果与这句话**不完全一致**，必须先分清：

| 事实 | 证据 |
|---|---|
| 判定**已经写好**：服务端过滤、可见≠可做、订阅续传各自有函数 | `authorization::filter_records` / `access_record` / `check_subscription`（P5 2.2，AZ01/AZ06 用例） |
| 判定**在生产零调用** | `authorize_stage` 的调用点全在 `tests/` 与 `audit_log` 用例内；`StageFacts` 4 处构造全在测试 |
| 装配来源**不存在** | 没有任何从 `SqliteStore` 读出 grants / members / customer_bindings 的函数 |
| 目标侧字段**已经就位** | `delivery_targets.customer_id`（016 迁移）与 `ScopedRecord::for_customer` 语义一致 |

所以缺口是**接线**，不是**判定**。这决定了本 ADR 只讨论三件事：入口唯一、装配边界、拒绝码分级。

## 决策

1. **`authorization` 是唯一入口，不新建访问控制模块，不扩 `StageAction`。**
   目标过滤走 `access_record(facts, actor, record, action, target, at)`，它一次给出
   `Invisible` 或 `Allowed(StageDecision)`——「不可见」与「可见但缺权」在类型上就分开，
   不允许调用方自己拼「先查再看」。

2. **新增装配端口 `StageFactsPort`（bod-app 内的纯函数 + 只读查询），负责把库里的
   grants / assignments / members / customer_bindings / revoked_at_revision 装进 `StageFacts`。**
   装配是**读**，不写库、不派发；端口只暴露「按主体 + 项目取事实」一个动作。

3. **目标映射固定为一条规则**：`DeliveryTarget` → `ScopedRecord { scope: 跟踪项 scope,
   customer_id: Some(target.customer_id) }`。跟踪项本身按 `scope`（project）判定，
   目标按 `customer_id` 判定。客户协作者只看自己客户的目标，父项目与兄弟目标一律不可见。

4. **拒绝码分三档，替换现在「一律 `BOD_API_DENIED`」**：

   | 情形 | 码 | 为什么不合并 |
   |---|---|---|
   | 未通过会话认证 | `BOD_API_DENIED` | 与主体无关，重试无用 |
   | 对象不可见 | `BOD_NOT_FOUND` | 用 403 会泄漏「这条存在」，AZ01 要求不产生差异信号 |
   | 可见但缺动作权 | `BOD_SCOPE_DENIED` | 调用方应改请求主体或申请授权，处置方式不同 |

5. **顺序：先 `GET /delivery-tracking/{id}`（只读），后写端点。** 读路径是目标过滤的最小
   完整用例；先做它，才能证明写入口的授权语义没有被顺手做松。

## 理由

- **不新建模块**：`filter_records` 与 `access_record` 已经有 AZ01/AZ06 的命名用例，
  再写一套「交付专用的可见性判定」会出现第二个真相来源，且两套判定必然在某次改动后分叉。
- **装配独立成端口**：`StageFacts` 是值类型，构造它需要读 5 组事实。把读取塞进
  `authorization` 会让纯判定模块依赖 `SqliteStore`，破坏「入口不访问 DB」的既有约束
  （`authorization` 模块头第一句）。
- **拒绝码分级**：合并成 403 是最省事的写法，也是 AZ01「不泄漏存在性」最容易被破的地方。

## 代价

- 每个 `/api/v1` 请求多一次事实装配（5 组小查询）。单机 SQLite 下可接受，但必须按请求缓存，
  不能在每个目标上重查一遍——目标数量增长时这是 N+1。
- `StageFacts` 目前是 `Vec` 线性查找；`customer_bindings` 超过数百条后需要索引化结构。
- 三档拒绝码是对外行为变化，客户端错误处理要同步（当前六条路由全 `planned`，改动成本最低的时机就是现在）。

## 撤销条件（可机械判断）

1. 出现**跨 Company 查询**（多 Company 单宿主），或远程节点需要自带判定——
   此时 `StageFactsPort` 必须换成远程授权服务，本 ADR 重评；
2. `customer_bindings` 单 Company 超过 **1,000** 条且装配 p99 > 5 ms——需要索引化，重评数据结构；
3. 需要「同一对象对不同主体给出不同**字段**投影」（不只是可见/不可见）——这超出 `ScopedRecord`
   的表达力，需要新的投影层，重评第 3 条。

## 代码体现（落地时才产生）

- 已有：`crates/bod-app/src/authorization.rs`（`filter_records` / `access_record` / `ScopedRecord`）。
- 待建：`StageFactsPort` 装配函数、`delivery_api` 的 `Principal` 传参、三档拒绝码常量。
- 当前 `delivery_api` 的 `note` 与 `DENIED_CODE` 在落地时必须同步改写，测试
  `planned_routes_point_at_the_unimplemented_handler` 会挡住「悄悄当已实现」。

## 决策补充（2026-11-22 晚 · v1.0 承接）

上面五条回答了「判定放哪、事实怎么装、拒绝码怎么分」，但**没有回答最后那个问题：
`Principal` 从哪来**。这一项一直悬着（A 单用户显式 / B 会话→成员映射 / C `X-Bod-Actor` 自报头），
`with_delivery(read, actor)` 因此没有生产调用者。v1.0 规格给出了依据，现在把它定掉。

### 6. 主体由宿主按本地身份确定，请求不得自报

**决策**：`DeliveryActor` 在宿主启动装配时构造，来源是宿主进程的本地身份（部署侧配置 +
运行账号）；`company_id` 与 `principal_id` 都不从请求体、请求头或查询参数读取。
接口层只接受「已确认的主体」，不存在「让调用方声明自己是谁」的入口。

**依据**（不是偏好，是规格条款）：

- v1.0 技术规格 §1：「互不信任租户按 **OS 身份或部署边界**隔离」。若主体可由请求头自报，
  隔离就退化成「谁声明谁就是谁」，与这句直接矛盾。
- v1.0 技术规格 §0.4：「先确定目标和对象可见性，再判动作授权」。可见性必须基于**已知主体**；
  主体待定就无法排序，四阶段判定（认证 → 立场 → 权限 → 目标粒度）第一步就断。
- v1.0 附篇 §7：执行身份、客户范围与读取权限在**每次受保护操作时重新校验**。
  可自报的主体无法被「重新校验」——因为没有独立于请求的权威来源。

**否决 C（`X-Bod-Actor` 自报头）**：它把「认证」与「授权」压成一步，且让审计归属可被调用方改写。
一份「谁批准的」记录，如果批准人由请求自己填，那它在纠纷里没有证明力。
这不是「实现更麻烦所以不做」，是它会**让已有的审计与撤权机制同时失效**。

**否决 B（会话→成员映射）**：当前没有会话表与会话生命周期，「会话」只存在于 SSE 连接上。
先造一套会话再从中取主体，等于为了取主体而新增一个持久化身份层——而这一层没有任何别的用途。

**采纳 A，但把它的代价写明**：
同一台机器上多个成员共用一个宿主身份时，**审计归属会记到宿主身份上**，
无法区分「张三做的」与「李四做的」。这条不是可以含糊过去的实现细节，
必须进支持矩阵的已知限制，且**不得**用「支持多用户」的说法掩盖。
真正需要多人区分的部署，走「按 OS 用户/部署边界隔离」（§1 已给出路径），不是加一个自报头。

### 撤销条件（可机械判断）

1. 出现**同一宿主内需要区分多个成员**的真实需求，且部署上无法按 OS 用户隔离——
   此时要引入独立的身份提供方（本地账户表或外部 IdP），本项重评；
2. 远程节点需要代表其用户提交命令，且宿主无法从链路身份推出主体——
   此时主体来源改为「链路双向认证结果」，仍**不得**回到请求头自报；
3. 工作台需要「以他人身份查看」——这是模拟/代操作能力，必须走单独的代操作凭据与双签审计，
   不得靠改 `Principal` 实现。

## 落地记录（2026-11-22 深夜 · P8 7.6.2）

第 6 条从「决策」变成「在生产路径上生效」，落点是三处，每一处都写明了**故意不做什么**：

| 落点 | 做了什么 | 故意不做 |
|---|---|---|
| `host_handshake::local_principal_id` | 启动时读一次本机账户名（`USERNAME` / `USER` / `LOGNAME`），逐字作为 `principal.id` | 不拼前缀、不折叠大小写、**不提供 `--as` 之类的覆盖开关**。覆盖开关等于把「谁是主体」交给启动者，而桌面环境下启动者与调用方常在同一进程树里 |
| `SqliteStore::open_existing_readonly` | 以 `SQLITE_OPEN_READ_ONLY` + `query_only` 挂载既有业务库；不建库、不迁移、不写 | 不跑迁移。库比代码旧时报 503（装配端口 `Unreadable`），不替业务库决定 schema 版本 |
| `bod serve --db <path>` | 显式路径必须存在，缺省只在 `$BOD_HOME/bod.db` 已存在时挂载；未挂载时 `/api/v1/*` 一律 401 | 不在默认路径建空库。建了空库，「路径写错」会伪装成「库里没数据」，每个请求都变成 404 |

**为什么只读挂载不违反 8.1「不打开第二个业务库」**：8.1 防的是**第二个写者**（双主、WAL 争用、
审计与业务写入没法同事务）。只读连接在 SQLite 层就写不进去，且 WAL 下读者与写者互不阻塞，
因此它是读副本而不是第二个写者。判据可以机械检查：`query_only` 一旦关掉，`store::tests::store_core::readonly_mount_*` 立刻失败。

**证据**（`crates/bod/tests/delivery_read_e2e.rs`，真实子进程 + 真实 TCP）：

1. 不带任何自报头 → `200`，两个目标都在（此前恒为 401）；
2. 换一个 id → `404 BOD_NOT_FOUND`（可见性按主体算，不按 id 存在与否算）；
3. 加 `X-Bod-Actor: someone-else` → 仍是 `404`（自报头不改变归属；若将来有人加了这个支持，这条会立刻变 200）；
4. 未挂载 → `401 BOD_API_DENIED`，且不替默认路径建库；
5. 显式指向不存在的库 → 启动失败、不留下空库与描述文件。

**遗留**（不改第 6 条，只记录）：`StageRequirement::Work` 仍只判 `target.assignee`，
撤权之后被指派者还能开发与回报进度；这属于「动作权限」的缺口，与主体来源无关，
已由 `store::tests::revoke::assignment_alone_still_permits_work_after_revocation` 钉住。
