# ADR-0009 业务库的写者归属：谁可以往库里写

- 状态：`proposed`（待项目负责人签署；本 ADR 不改任何代码路径）
- 日期：2026-11-23
- 决策者：待签（建议人：架构评审）
- 关联：`openspec/changes/p8-delivery-tracking`（proposal §5 非目标、tasks §7.5 / §7.7）；
  V2.9.7 产品方案「宿主独占写锁和运行 epoch 防双开」；ADR-0007 第 6 条
- 取代：无

## 场景

p8 的非目标里写着一条硬边界（`openspec/changes/p8-delivery-tracking/proposal.md`）：

> 不建第二个业务库、**不建第二业务写入者**（§5 单写事务不变）。

7.6.2 之所以能成立，靠的正是这条边界没有破：`serve --db` 用
`SqliteStore::open_existing_readonly`（`SQLITE_OPEN_READ_ONLY` + `query_only`）挂载既有库，
在 SQLite 层就写不进去，因此它是**读副本**而不是第二个写者。

7.5 要求的却是把 `POST imports` / `links` / `observations` / `drafts` / `send` 逐条转 `served`。
一旦转了，控制面进程必须持有**可写连接**——它就成了第二个业务写入者。这不是实现细节，
是 p8 自己写下的非目标。所以 7.5 之前必须先回答本 ADR。

## 现状（本轮实测，不是引用旧结论）

| 事实 | 证据 |
|---|---|
| 规格要求「宿主独占写锁和运行 epoch 防双开」 | `docs/bod-V2.9.7-智能体协作开放平台完整产品与开发方案.md` 备份与恢复一节 |
| 仓库里**没有**宿主写锁，也没有 running epoch | `grep -rn "lock_file\|write_lock\|running_epoch" crates/bod-app/src` 只命中 `catalog_upgrade` 的事务级 `holds_write_lock` 与 `handoff_manifest` 交接清单里的 `lock_file` 字段，都不是宿主锁 |
| 因此「单写者」今天是**约定**，不是机制 | 无任何断言能发现两个进程同时写 |
| CLI 的三个「只读」命令其实是写者 | `bod observe/tracking/sources --db` 都调 `SqliteStore::open`，而 `open` 每次打开都跑全部 20 个迁移、并 `create_dir_all(parent)`；help 文本却写「只读」 |

最后一行是这一轮新发现的：**「第二个写者」其实已经存在，只是它写的是 schema，
而且它的 help 文本在否认这件事。** 这比「将来要不要开 POST」更该先修——因为它现在就错。

## 选项

### A. 控制面是唯一写者

`serve --db` 改用可写连接；同一提交里落下「宿主独占写锁 + running epoch」；
CLI 的写入改成连到控制面，或退化为只读。

- 符合规格原文，也符合「工作台调接口」的产品方向。
- 代价：锁与 epoch 是新的持久化机制（要处理僵死锁、重启接管、双开被拒的退出码），
  不是接线；且 p8 的「不建第二业务写入者」这条非目标要正式改写。
- 谁会发现双开：`serve` 第二次启动失败（需新增断言）。

### B. 写入只走 CLI，HTTP 只读

`serve --db` 保持只读挂载；`POST` 五条路由保持 `planned`，并在 `x-bod-status` 与
支持矩阵里写明「本项目决定写入不经 HTTP」；交付写入由 `bod tracking import` 等子命令承担。

- 不破 p8 非目标，不引入未实现的锁；立刻可用，因为 CLI 本身就是真实调用者。
- 代价：`GET` 视图里的 `allowed_actions` 会长期为空（动作码现在绑在 HTTP 路由上，
  `is_served_action` 只认 `served`）。要么把判定改成「本进程有入口」，要么在契约里
  声明「动作在 CLI，视图不给动作」——不论哪个，都必须在转 served 之前改，
  否则视图会开始宣称「可做」而实际做不了。
- 谁会发现双开：`serve` 只读，写不进去；但 CLI 之间仍无锁（见下面「遗留」）。

### C. 混合：少量写路由开在控制面

只让 `imports` / `observations` 走 HTTP（执行端推送），其余走 CLI。

- 复杂度等同 A（照样要锁，否则双开无防护），收益是「执行端不必装 CLI」。
- 不建议：把「要不要锁」变成「哪些路由要锁」，判定更碎，且没有任何一条真实需求当前要求
  HTTP 推送观察。

## 决策

建议 **切片 1 采用 B，把 A 作为 p9/p10 的目标形态**。

理由是可验证的，不是偏好：

1. B 的每个写入动作都有真实调用者（CLI），符合「生产调用点先于状态翻转」的纪律；
   A 的调用者（工作台/执行端）现在不存在，先做 A 会得到一个只有测试在写的写入口。
2. 锁与 epoch 无法与「开写路由」分成两次提交，否则中间态就是无防护双开。B 让这件事
   整体推迟到有真实需求时，那一次提交里补齐。
3. B 不改写 p8 的非目标；A 需要改写，而改写非目标应当由需求驱动，不是由排期驱动。

**切换到 A 的触发条件**（写清楚，避免无限延期）：出现「非本机进程必须写入」的真实需求
——工作台改由 HTTP 提交草稿/发送，或执行端需要 push 观察。届时同一次提交里必须包含：
宿主写锁、running epoch、双开被拒的用例、以及 p8 proposal 非目标的改写。

## 后果

| 项 | B 之下必须做的事 | 否则 |
|---|---|---|
| `allowed_actions` | 判定从「路由是否 `served`」改为「本进程是否真有入口」，并在 `authorization` 里给交付域动作补需求映射 | 视图继续宣称可做，而 HTTP 做不了 |
| CLI 三个只读命令 | `observe` / `tracking` / `sources` 改用 `open_existing_readonly`；缺库报错而不是建库 | 「只读」是假的，且每次调用都在跑迁移 |
| 支持矩阵 | 写明「交付写入不经 HTTP」，不得写成「接口已全部可用」 | 评审会把 planned 当成未完成而不是决定 |
| 7.5.2 | 五条 `POST` 保持 `planned`；转 served 的前置改为本 ADR 改判为 A | 7.5 与 7.6.2 互相矛盾 |

## 遗留（本 ADR 不解决，必须记录）

即便选 B，**两个 CLI 进程之间仍然没有锁**。SQLite WAL 会把写串行化，不会损坏数据，
但「宿主独占写锁 + epoch」这条规格要求仍未实现。这不是本 ADR 能顺手解决的：
它需要一次独立的「单实例锁」设计（锁文件位置、僵死检测、重启接管、与 `$BOD_HOME` 的关系）。
在它落地之前，支持矩阵不得声称「已防双开」。

## 撤销条件

1. 出现触发条件（非本机进程需写入）而未切 A → 重开本 ADR，不得以「先开了再说」绕过。
2. 若选 B 之后发现 CLI 无法承担某个写入（例如必须由执行端在无人值守时提交观察），
   该条路由单独走 A 的机制，但锁与 epoch 必须先落地。
3. 若「单实例锁」独立设计落地，可重新评估 A 的成本，那时 A 与 B 的价差主要在 CLI 改造，不在锁。
