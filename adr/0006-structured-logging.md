# ADR-0006 结构化日志与业务审计分工

- 状态：accepted
- 日期：2026-11-21
- 对应评审条目：CR-002
- 影响文件：`crates/bod-app/src/telemetry.rs`、`crates/bod-app/src/audit_log.rs`、
  `crates/bod-app/src/observability.rs`、`crates/bod-app/migrations/015_audit.sql`、
  `crates/bod-app/Cargo.toml`

## 背景

规格 §3 把 `tracing` 列为核心栈；§8 要求「日志和审计保留关联 ID、授权依据、范围、
决策与原因并脱敏」；§9 要求「分别呈现阻塞原因、队列积压、待核实外部动作数量和等待时长、
预算预留、事件缺口，以及端到端延迟」。

在此之前全仓零日志设施：控制面用 `eprintln!`，`StageAudit` 只活在内存里随请求结束消失。
CR-002 的三步建议是：先定审计 schema 落表 → 再引 tracing → 指标先做「能从现有表算」的部分。

## 决策

### 1. 日志与审计是两条通道，共用 `correlation_id`

| | 业务审计 | 诊断日志 |
|---|---|---|
| 载体 | `audit_events` 表 | stderr（`tracing`） |
| 回答 | 谁基于什么证据做了什么决定 | 这次请求为什么慢/失败 |
| 保留 | 长期、不可改写、可查询 | 可滚动丢弃 |
| 写入时机 | 与业务事实**同一事务** | 事件发生时 |

不合并的理由：审计要能被 `SELECT` 聚合（拒绝率、按动作分布），日志要能低成本高频写。
用日志文件冒充审计，等于放弃查询；用表冒充日志，等于让每次调试都写一次磁盘事务。

### 2. 关联 ID 由调用方生成，格式 `req-<实例短号>-<进程内序号>`

用序号而非随机串：同进程内的顺序可读可排，排查「两条并发请求谁先到」才有意义。
实例短号防止多实例日志汇总到一处时撞号。`AuditEvent::from_stage` 是
`StageDecision → AuditEvent` 的唯一入口——两处各自拼字段是审计漂移的常见来源。

### 3. 审计表只 INSERT，库层加不可变 trigger

与 `decisions`（014 迁移）同款。应用层只 INSERT 是事实，但「发现了也改不了」比
「我们不会改」可靠。绕过 trigger 的路径（备份恢复、外部 sqlite3）由 `--check` 之外
的读侧严格性兜住：读回时表外动作/表外决策直接报错，不静默回退。

### 4. 观测读模型只读，算不出来的项显式列 `not_measured`

`observability::snapshot` 不新增采集、不改写入路径，只对既有表做 GROUP BY。
当前三项算不出来并写进报表：事件缺口（内存 feed 无持久序列）、端到端延迟
（渠道确认未落库）、阻塞与待核实的**时长**（缺 `blocked_since_ms` / `dispatched_at_ms`）。

**留白会被读成「没有缺口」**，所以宁可多一段「未测量」，也不填 0。

### 5. 不引 `env-filter`

`tracing-subscriber` 的 `env-filter` 会把 `regex` + `aho-corasick` 拖进生产依赖树。
本仓只需要按级别过滤（`BOD_LOG=debug`），用 `with_max_level` 足够。

## 被否的方案

| 方案 | 否决理由 |
|---|---|
| 审计写 JSONL 日志文件 | 不可查询：问「上周有多少次 accept 被拒」要 grep 整个目录，且无法与业务事务对齐 |
| 控制面自己开 SQLite 写审计 | 违反既有硬约束「不打开第二个业务库」（`serve` 的注释，8.1） |
| 审计与业务事实分事务写 | 会出现「业务回滚了、审计里记着发生过」，比不记更糟 |
| 观测指标自造计数器 | 计数器与库现状会漂移；先做「能从表算」的部分，算不出的写明原因 |

## 代价

- 审计表只增不删。当前没有归档策略，行数增长后需要按时间归档（见撤销条件 3）。
- 每个请求生成一个字符串 ID（一次格式化 + 一次原子加），在 p99 ≤ 10 ms 的关键事务外，
  属可忽略量级；但它确实不是零成本。
- 控制面日志的字段清单固定为 method/path/status/outcome/elapsed/ID。
  要加字段（如 user agent）得先回答「会不会把令牌带进来」。

## 撤销条件（可机械判断）

1. `BOD_LOG` 不足以定位问题，出现**至少两次**「因为无法按 target/模块过滤，只能临时改代码加
   `if` 才能看清」的调试记录 → 引 `env-filter`，并重新评估 regex 依赖的准入。
2. 审计表行数 > 500 万，或 `append_audit_event` 的写入使关键事务 p99 超过 10 ms → 引入按
   年度/月度归档表（SQLite 用 `ATTACH` + 定期搬迁），不加分区扩展。
3. 单个宿主进程的日志量 > 1 GB/天 → 引入滚动与采样，并区分「必须全量」的控制面拒绝日志与
   「可采样」的普通请求日志。

## 当前未完成（不假装完成）

- **审计表尚无生产写入者**：§6 的 5 个业务接口与 §11 的交付跟踪都还没实现，`authorize_stage`
  在生产路径零调用（只有测试调用）。表、仓储、校验、不可变约束都已就绪，接上写路径即可，
  但「现在库里没有审计行」是事实，不是配置问题。
- 控制面请求日志已落地（`tracing`），但它记的是**传输层**事件，不是业务审计。
