# ADR-0002 工作台暂不引入前端框架

- 状态：`accepted`
- 日期：2026-11-21
- 决策者：项目负责人（本次评审后批准）
- 关联：评审报告 CR-004（DTO 单源）、评审报告 §五「前端栈偏离」

## 场景

V2.9.6 技术架构规格 §2/§3 描述「Tauri 2 壳加载 **Vue** 静态资源」，
并要求「前端通过 openapi-typescript 使用 utoipa 生成的契约」。

实际实现：`apps/workbench` 是 TypeScript + 原生 DOM，零运行时依赖，
构建只有 `tsc`，测试跑 `node --test`。无 Vue、无 Vite、无 utoipa、无 openapi-typescript。

## 决策

暂不引入前端框架，保持零构建链（`tsc` + `node --test`）。
**但契约单源不豁免**：CR-004 仍要做，只是做法不依赖 utoipa 全链路。

## 理由

1. **当前界面复杂度配不上框架的固定成本**。工作台只有状态展示与 3—4 个动作，
   无路由、无表单校验链、无列表虚拟滚动。Vue 的收益（响应式、组件复用）在这个规模上
   接近零，而成本（构建链、版本升级、调试心智）立刻要付。

2. **零依赖让前端测试与后端 CI 同构**。`node --test` 直接跑 `.ts`（经 `tsc` 或
   node 的类型剥离），不需要浏览器、不需要 jsdom、不需要 dev server。
   一旦引入 Vite，测试就得配 bundler 插件，CI 时间与不稳定因素都上升。

3. **真正的痛点是类型来源，不是渲染方式**。规格要的是「契约单源」，
   当前问题是前端手写 `interface` 与后端 DTO 无机制保证一致——**换 Vue 不解决这个问题**。
   先做 CR-004 才是对症。

## 代价

- DOM 操作逻辑随界面复杂度线性上升，缺少组件抽象后重复代码会增加。
- 无响应式：状态变化要手工重绘，漏一次就是界面与数据不一致。
- 无法直接使用 Vue 生态的表格/表单/图表组件。

## 撤销条件（可机械判断，任一满足即重评）

1. 出现**第 3 个可编辑表单**（当前 0 个）；
2. 需要**客户端路由**（当前 0 条路由）。

重评时优先评估 Vue / Lit / Svelte，且**必须先完成 CR-004（DTO 单源）**，
这样换框架不需要重写类型定义。

判断方式：表单数与路由数直接看 `apps/workbench/src` 里是否有对应模块，
不依赖主观判断「界面复杂了」。

## 代码体现

- `apps/workbench/package.json`：无 `vue`、无 `vite`。
- `apps/workbench/src/connection.ts`：手写 `interface`（CR-004 的整改对象）。
- 构建脚本：`tsc`；测试：`node --test`。
