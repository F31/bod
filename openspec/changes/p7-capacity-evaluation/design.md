# Design: P7 容量评估

## Context

动机见 `proposal.md`；前六阶段已交付可测系统与支持矩阵。P7 是评估与决策门，不是功能开发，也不预设引擎迁移（§38、§40.4）。

## Goals / Non-Goals

- 目标：产出可复现的性能基线、瓶颈定位与方案对比；把「是否迁移」变成有证据的审计决定。
- 目标：明确哪些目标仍是 Target/Unverified，哪些预算在两阶段后可冻结。
- 非目标：为了达标降低 SQLite 同步、事务边界、授权检查或接受门禁；把实验室目标写成产品承诺；未授权切换到 PostgreSQL 或外部服务。
- 非目标：重新设计前面阶段的业务能力。

## Decisions

1. **先固定测量条件。** 首轮统一 Linux x86_64、8 核、16 GiB、本地 NVMe，记录 OS、CPU、Rust/构建参数、SQLite 同步策略、数据规模与缓存冷热；Windows/WSL2 单独报告（§38.2）。
2. **形态分报。** headless、可选 Web 宿主、Tauri 桌面与移动包分别记录压缩/展开体积、平台、静态/动态链接与资源；Web 宿主 RSS 不冒充桌面总内存（§38.2、§41.9）。
3. **四类毕业信号。** RTO 不达标、单写争用、索引/数据体积压力、实际多机写入或容灾需求分别测量；任一信号需有原始报告与可重跑命令，不能用日事件数单一阈值替代（§40.4）。
4. **候选方案先比较再决定。** 索引/批处理/存储优化、执行节点扩展、PostgreSQL、外部持久执行服务分别对比迁移代价、运维负担、故障语义与恢复证据；不能把 DAO 替换等同语义兼容（§11.7、§40.4）。
5. **预算冻结需两阶段。** 连续两个可比较阶段的实测后才冻结正式预算；超标先定位默认依赖与结构，不降低正确性凑数字。
6. **决定可审计。** GraduationDecision 记录瓶颈、样本、环境、候选对比、选定方案、回滚路径、未覆盖条件与责任主体；不支持的能力保持 Planned，不因容量报告扩大支持矩阵。

## Risks / Trade-offs

- [测量与真实负载不同] → 样本注明生成方法与覆盖范围，外部人可复跑；无法覆盖的部署形态标 Unverified。
- [以性能优化牺牲正确性] → 任何同步/事务/授权变更需走原 I/G 门禁回归，不能在 P7 内静默生效。
- [引擎迁移被当作唯一解] → 优先索引/批处理/存储优化；多机需求也必须对比执行节点扩展。
- [指标样本不足] → 报告样本数、失败原因与未测项，不以单次峰值或历史估算下结论。

## Migration Plan

本 Change 只新增测量与决策记录，不对业务数据做迁移。若决定进入 PostgreSQL 或外部持久执行服务，必须另建 Change，登记 migration_id/checksum/兼容窗口、单写次序与真实并发测试、备份恢复演练和回滚路径；旧样本库升级通过后方可宣称兼容。

## Open Questions

- 真实生产负载样本与维护窗口由试点授权提供；缺失时使用脱敏合成负载并明确标注外推限制。
- 冻结后的预算数值由两阶段实测结果确定，不在本设计文档中预设达标结论。
