# Proposal: P9 组织代次与缺口驱动的改组

## Why

V3（v1.0 规范）把能力重新分成三层：核心宿主（T/C）、**自适应协作扩展（D/A）**、
路径与执行端（S/H）、扁平协作（F）。技术规格 §9 把「在线协作」定为第二切片，验收
D01–D06、D08–D09、P01–P03。

当前代码离这个切片有三处硬缺口，且都不是「再多写点判定」能补的：

1. **没有「缺口」这个对象。** 交付域能记录目标、观测与覆盖结论，但「哪个结论被卡住、
   缺哪种观测、下一次复核条件是什么」只存在于函数返回值和自然语言里。没有持久化的缺口，
   「按缺口改派」就无从触发——决定改组的触发源必须先入库。
2. **没有组织代次。** `collaboration_plan`（1279 行，生产不可达）有执行图准入与租约判定，
   `takeover_intent` 有接管阶段，但**没有任何字段表示「这是第几代分工」**。于是
   v1.0 D4 与 §3 的核心不变量「旧代次的迟到结果不能推进当前状态」在结构上无法表达。
3. **没有计算档位。** 附篇 §4 的 G0–G3 与 L1–L3 在 `bod-app`/`bod-core` 中零命中。
   D08 用例（同一目标分别以确定性输入和冲突新输入提交）要求档位可观察、可收缩，
   当前没有任何地方能记录「这次为什么用这个强度」。

三条都指向同一个后果：**自适应协作目前只有判定函数，没有可追溯的运行记录**，
因此验收用例无法产出「改组差量 + 代次 + 档位轨迹」这类证据。

## What Changes

- 新增**缺口对象**（`delivery_gaps` / 或复用现有缺口投影的统一表）：绑定被阻塞的目标或工作包、
  验收条件、已知证据修订、所需观测与下一次复核条件；按 (目标, 规则, 触发源, 观察窗口) 去重；
  五态：待补证 / 待授权 / 待外部事实 / 已解决 / 已被新修订取代。
- 新增**组织代次**：`work_package` 的当前代次与认领绑定；`organization_generations` 记录
  每次有效改组的缺口、候选、排除理由、职责差量与授权/预算复核结果。无有效差量不加代次。
- 新增**计算档位与治理级**纯判定（`bod-app::compute_tier`）：G0–G3 × L1–L3 × 风险三轴独立，
  按技术 §4.1 的转换表给出「允许的转换 + 退出边界」；档位变化写轨迹。
- 把 `collaboration_plan` 的执行图准入**接到真实缺口与代次**上，使其从 orphan 变为生产可达；
  同时落地执行者主动移交意图（技术 §3.1）的入库与评估状态。
- 新增 capability `adaptive-collaboration` 的 spec delta（需求见 `specs/`）。

## Impact

- 迁移：新增 2 张表（缺口、组织代次），`work_package_states` 或认领表增加代次列。
  已应用迁移**不得原地改写**（`ChecksumDrift`），因此新列一律走新迁移。
- 代码：新增 `store/gaps.rs`、`store/generations.rs`、`compute_tier.rs`；
  `collaboration_plan` 从 orphan 转为被 `store`/命令层引用。
- 契约：本 Change **不新增 HTTP 路由**（切片 2 的入口在切片 1 的命令层之上），
  因此 `verification/openapi.json` 不变。
- 门禁：`I-72`（两条入口同结论）不受影响；新增条款映射登记到
  `docs/reports/v3-spec-review-and-refactor-plan.md` §7.2。

## Non-Goals

- 不做证据共源计数（C04/D02/A05）、不做影响重验的持久化索引（D03/P02/A-T1）——留 p10。
- 不做观测器暂停/预算升级（D04/D05/A-T4）——留 p10。
- 不做离线证据包与复演（V05）——留 p11。
- 不做策略校准发布（V06/D07/P05）——留 p12。
- 不改 `authorization` / `coverage_receipt` 的语义（技术规格 §8 要求复用）。
