# Design: P4 实际运行交付

## Context

动机见 `proposal.md`；P3 提供集成接受证据，P4 把候选交付推进到实际环境和客户回执（§28—29、§21.7、§21.17）。本阶段不开放团队或远程能力。

## Goals / Non-Goals

- 目标：一条真实业务流程在最终制品与环境组合上通过；三个产品对照场景有可核对基线。
- 目标：覆盖回执能区分已部署、待安装、已回滚与未知，回滚后能纠正已发出的答复。
- 非目标：自建 CI、测试框架、浏览器引擎或模型评测基础设施；P5 团队权限、P6 远程/移动、P7 引擎迁移。
- 非目标：把 hash、签名或 PDF 导出解释为法律认证、仲裁效力或业务正确。

## Decisions

1. **VerificationPlan 是绑定层。** Scenario/Criterion 映射到现有脚本/CI/API/浏览器流程/人工检查；bod 不自建执行引擎，报告必须记录 commit/digest、规则版本、环境、执行者与时间（§28.7）。
2. **一次构建按 digest 晋升。** BuildRecord 记录源码 commit、构建定义、工具链、锁文件、平台、参数摘要与输出 digest；平台特定重建生成新记录，不静默复用验证结果（§28.3）。
3. **清单不可变。** Manifest 冻结具体修订，变更产生新修订；对外交付不引用浮动最新版本。内部取决于原生权威存储，bod 只固定引用与摘要（§21.1、§21.4）。
4. **证据视图最小化。** internal/customer/audit 三种视图字段级披露；签名只覆盖明确 payload，脱敏后不声称原连续哈希链仍成立（§21.7、§21.14）。
5. **审批锁定实际参数。** ReleasePlan 固定 Manifest、环境、部署方式、迁移、验证与停止条件；审批绑定 digest/环境/参数/有效期，目标变化使原审批失效（§29.3）。
6. **部署与运行分开。** Pending/Running/Verifying/Succeeded/Failed/Unknown 是部署状态；发出请求不等于成功。回滚只恢复声明可回退资源，其他走前向修复（§29.3）。
7. **覆盖按目标元组核对。** 项目、环境、部署单元或客户组、制品摘要共同决定覆盖；未知人群、未同步开关或缺制品对应关系显示覆盖待核实（§29.7）。
8. **回执与结算分离。** FeedbackReceipt 记录客户确认/异议/复开；成本按实际 invocation 结算，验收触发付款时用有效回执关联合同里程碑与幂等键（§21.17）。

## Risks / Trade-offs

- [CI 成功但组合不同] → 合并前重建候选验证，最终接受绑定实际 commit/digest（§21.9）。
- [回执早于部署事实] → 目标交付与客户响应分开呈现，缺证据标待核实，发送前重查授权与最新修订（§29.7、§30.10）。
- [回滚不可完全撤销] → 声明可回退范围，不可逆迁移与数据写入走前向修复；历史证明保留并追加纠正通知。
- [签名被误读] → 报告分项展示包完整性、签发者身份、证据关联、可执行复验与业务验收，自签标明未建立外部信任。

## Migration Plan

追加 verification_plans、build_records、manifests、publications、environment_refs、release_plans、delivery_targets、feedback_receipts、coverage_observations 与对应事件。历史成果无 Manifest 引用时标不可完全复现，不补造 hash。回滚保留 P0—P3 数据与接受记录，发布队列停止新发布但不清空证据。

## Open Questions

- 首批接入的 CI/制品/环境连接器及其版本由试点授权确定；不改变验证证据与审批绑定规则。
- 客户证明页样式可在试点调整，但四类结论与缺证据标待核实属于规格，不在本层变动。
