# Design: P3 变更与有效协作

## Context

动机见 `proposal.md`；P1 提供单执行者与隔离工作区，P2 提供接续与负责人切换。P3 只解决「同一规格变化下多个工作包如何共享基线并有效集成」（§26—27、§21.11—12）。

## Goals / Non-Goals

- 目标：一个共享接口变化能定位受影响组件与任务、生成有限重验，并在真实提交组合上完成集成接受。
- 目标：共享 Agent 不串会话，默认扁平协作不强制管理层，计划由宿主确定性校验后形成不可变图修订。
- 非目标：第二运行时接续之外的能力扩张、CI 制品/环境发布、团队权限与 Catalog、远程与移动、容量引擎迁移。
- 非目标：完整静态/语义分析全仓库；初期优先接口、迁移、公共配置与明确规格关系。

## Decisions

1. **规格以 Git 文件为准。** OpenSpec 文档按 Change 组织，bod 保存确定修订与映射；tasks.md 勾选是进度投影，不是验收证据（§26.2、§26.6）。
2. **稳定任务 ID。** task-map 保存稳定 ID、来源路径、锚点、指纹与匹配状态；无法唯一匹配进入 Unresolved 并人工确认，不按行号自动绑定（§26.3）。
3. **工作包按可验证输出划分。** 先按契约/模块/验证边界拆包，再按能力和 Profile 建议分配；不按 Agent 数量或 tasks.md 行数机械平均（§26.4）。
4. **PlanProposal 与 PlanRevision 分离。** 顾问只交提案，已委任负责人在 Grant 内提交安排；宿主校验无环、需求/场景映射、共享资源冲突与权限后形成不可变图修订（§26.9）。
5. **依赖边分确定性。** requires/implements/verifies/built_from/deployed_to 等显式边与 Agent 推测边分别记录来源和置信；「未找到依赖」不表示无影响（§21.11）。
6. **选择性重验有界。** 先按确定边计算候选，再按需分析语义；经授权策略或人工接受后创建有限重验工作，去重键关联变更与评估修订，限制循环（§21.12）。
7. **合并队列串行化共享生效点。** 工作包在独立 worktree 生成候选，契约工作包先行；合并前在最新目标上重建候选并重新验证，带 expected target commit 更新 ref（§27.3、§25.12 计划）。
8. **默认扁平。** 按依赖通信而非组织汇报关系；普通答疑按职责路由，改变需求/权限/验收的答案走各自修订流程（§7、§26.8）。

## Risks / Trade-offs

- [映射维护超过重验收益] → 初期只映射明确规格/接口/配置关系，用实际漏项与返工数据校准支持格式（§1.6）。
- [推测边被当事实] → 推测关系带依据与置信，不能直接改变接受状态；显示 unknown 不自动清空。
- [集成组合不一致] → 合并前重建候选验证，使用实际 commit 组合证据，不沿用候选分支绿灯（§21.9）。
- [共享 Agent 串会话] → 资源键含 Company/Project/委任身份，Agent 全局并发另行约束（§9.10）。

## Migration Plan

追加 spec_bindings、task_mappings、impact_assessments、merge_requests/merge_evidence 与 revalidation_plans 表和事件。历史 Change 无稳定映射时标 Unresolved，由规格负责人确认后再绑定；不自动按文本行号猜测。回滚保留已有 P0—P2 数据与工作区，合并队列停止新合并但不清空候选。

## Open Questions

- 首批接入的真实项目接口样本由试点确定；不影响依赖边分类与重验门禁。
- 协作建议的呈现方式可在工作台调整，但提案/安排权限边界与任务映射身份属于规格，不在本层变动。
