# Design: P8 双入口交付

## Context

动机见 `proposal.md`。约束来自三处，任何设计都不能绕过：

- V2.9.8 §11：两条入口共同使用覆盖投影，同一组有效证据应得出同一结论；路径在 OpenAPI 冻结时定稿。
- §5 单写事务：关联来源、目标与回执意图在**现有 Company 单写事务**内提交，不新建第二个写入者。
- 仓库现状：`bod-app::coverage_receipt::judge_coverage(&CoverageInput) -> CoverageVerdict` 已是纯函数，
  结论可复用；但它是当前 15 个零引用模块之一，只被漂移检查「提到」，没有真实调用方。

## Goals / Non-Goals

- 目标：外部导入能独立成立（无内部 Run/Attempt/审批），且与内部研发路径给出同一覆盖结论。
- 目标：重复导入不产生重复回执、不覆盖已登记的外部来源；跨项目同名 PR、跨客户同名环境分别解析。
- 目标：草稿保存与发送彻底分离；证据或授权变化后旧草稿不能发出。
- 非目标：模型调用、渠道 SDK 抽象、多租户权限模型（P5）、远程节点（P6）。

## Decisions

### D1 覆盖判定只做一次，两条入口共用

`judge_coverage` 作为**唯一**判定入口，两条入口都先把各自的原始事实规范化成 `CoverageInput`：

| 入口 | 规范化时补齐 | 不许做的事 |
|---|---|---|
| 内部研发 | 从 WorkPackage/Attempt/Accept 取证据 | 不得因为「有内部运行」就提高证据等级 |
| 外部导入 | 从来源修订、制品摘要、人工补证取证据 | 不得因为「没有内部运行」就降级或跳过核对 |

「同一结论」的判定方式：同一组 `CoverageInput` 字段值 → 同一 `CoverageVerdict`。
这条可以用纯函数直接测（I-72），不需要两边端到端跑完才敢说成立。

### D2 来源身份是五元组，不是 URL

身份 = Company + Project + 连接实例 + 来源对象类型 + 提供方稳定对象 ID。
只有 URL 或纯文本时**进候选**，由负责人确认后才成为身份。
代价：导入路径比「存个链接」麻烦得多；收益：跨项目同名 PR 不会互相覆盖。

两条去重语义分开：幂等键管「同一次命令重放」，来源身份管「不同命令导入同一对象」。
把两者合成一个键，会出现「重放被当成新导入」或「不同对象被当成重放」。

### D3 跟踪项不依赖内部 Attempt 外键

跟踪项必须能独立成立。实施前先盘查真实 schema/DAO/查询/UI 是否强制内部外键：

- 若允许独立成立 → 复用已有关系；
- 若受限 → 按 §33.7 做增量迁移或显式关联表，并用**真实旧库**验证：旧运行仍可追溯、
  外部记录可无运行、重复导入无重复回执。

禁止路径：为了满足外键而创建假 Attempt。那是在权威记录里写假数据，比缺功能严重。

### D4 草稿保存与外发是两条路径

草稿只写「目标 / 收件范围 / 证据修订 / 引用 / 缺口 / 文本修订」，保存动作**不产生任何出站副作用**。
发送要在两个生效点各查一次：命令受理时、出站工作者真正发时。两次之间证据或授权变化 →
旧草稿进待重审并提示差异，不允许「已入队就照发」。

发送结果与渠道送达分开记录：提交成功只表示意图已登记；回包丢失先对账，保持发送状态未知，
不推断为失败也不重发。

### D5 端点先冻结再实现

§11 的 6 个操作先带 `contract` 进路由表并重生成 `verification/openapi.json`，
路径冻结后才写 handler。理由：路径改名对客户端的破坏远大于实现顺序调整；
而冻结的成本是一条命令（ADR-0004 的黄金比对）。

冻结时定下的两点（实施后补记）：

- **产品接口单独一张表**（`delivery_api::routes`，前缀 `/api/v1`），不并入控制面
  `ROUTES`。分发层按前缀分流。理由是鉴权语义不同：控制面凭据是本机会话密钥，
  §11 要按 §34.12 的主体与目标判定；混在一张表里，文档会把两者写成同一种鉴权。
- **`x-bod-status`**：每条操作声明 `served` 或 `planned`（`Contract.status`，无默认值）。
  计划中操作一律 `planned` + 声明 501，handler 只有 `not_implemented` 一个；
  测试断言「planned 必须声明 501、served 不得声明 501」，实现落地时必须改状态。

当前鉴权只到会话级（`Auth::Bearer(BOD_API_DENIED)`），§34.12 未实现——
这一点写在每条路由的 `note` 里，也写进文档的 operation description。

### D6 更正是独立对象，不是对原答复的改写

已外发的答复不可修改，只能被追加更正。三条理由，都影响实现形态：

- **追加式**：原答复、原证据引用、原时点确认各自保留原值；更正对象引用它们而不覆盖。
- **覆盖范围由系统判定**：`complete` 只有在系统能枚举「已知下游」时才成立；枚举不出就是
  `partial`。这一点交给调用方声明等于让最想说「已全部通知」的人来决定这件事。
- **不提供删除**：能删的更正就不是追加式记录。要撤销更正的更正，仍然只能再追加一条。

### D7 观察委任是独立对象，且「陈旧」是状态不是措辞

主动持续观察必须有独立委任（目标、期限、频率、预算、允许动作、停止条件），
与执行指派分开记录。两条实现约束：

- **入口处拒绝，而不是运行中停止**：无委任时在启动点就不建观察；先跑起来再停，
  会先产生一份没有授权的证据，撤都撤不掉。
- **「陈旧 / 未知」必须是可判定的状态**：视图要能区分「结论现在成立」与「结论曾经成立」，
  否则前端只能拿旧结论填，而填了以后没有人能看出它是旧的。

## Risks / Trade-offs

| 风险 | 处理 |
|---|---|
| 旧库强制内部外键，迁移面比预期大 | 先盘点再动；必要时拆成两个切片（读路径先通、写路径后迁） |
| `coverage_receipt` 是零引用模块，接线时才发现设计与真实数据不匹配 | 首切片就用真实数据喂 `judge_coverage`，不先写「演示用」聚合 |
| 渠道无幂等能力时重复发送 | 标待核实 + 人工对账，不假装有 exactly-once |
| 6 个端点一次进表，开放文档的组件命名成为约束 | 组件名用聚合名（`DeliveryTracking`/`DeliveryDraft`），不用端点名 |

## Migration Plan

### 2.1 盘点结果（只读，2026-11-21；不改代码）

盘查范围：15 个迁移（50 张表）、`store.rs` 的 171 个查询函数、`apps/*` 全部前端源码。
结论先说：**没有任何外键指向 `attempts`/`runs`**，所以 D3 不需要靠迁移来「解绑」；
真正的阻断点只有一处——接受记录表把内部工作包修订写成了 `NOT NULL`。

| 检查项 | 实测 | 对 D3 的影响 |
|---|---|---|
| 外键约束 | 全库仅 1 条：`wake_receipts` → `work_queue(company_id, queue_key)`；**无一条指向 `attempts`/`runs`** | 跟踪项可独立成立，无需放宽或删除约束 |
| 强制内部身份的列 | `attempts.run_uid`、`invocations.run_id/attempt_id/binding_id/fencing_token`、`handoff_snapshots.source_attempt_id`、`takeover_intents.from_attempt_id` 均 `NOT NULL` | 这四张表只能装内部运行；外部导入不得借用（借了就得编 ID） |
| 接受记录 | `acceptances.work_package_revision` / `input_baseline` / `artifact_revision` 均 `NOT NULL`；`work_package_states` 主键为 `(issue_uid, revision_id)` | **阻断点**：外部交付没有内部工作包，写入必须编一个 WPR——正是 D3 禁止的路径。因此外部回执不复用 `acceptances`，另表承载 |
| 制品 | `artifacts.project_id NOT NULL`，无 attempt 列；`artifact_revisions.produced_by` 是自由文本 | 可复用：外部制品按项目归属登记，`produced_by` 记来源 |
| 验证记录 | `verification_records.revision_id NOT NULL`，指向制品修订 | 可复用：外部证据挂在制品修订上 |
| 查询/JOIN | `list_project_invocations`、`list_run_invocation_states` 经 `JOIN runs ON … JOIN issues` 过滤；`list_project_acceptances` 经 `JOIN artifacts` 取项目 | 前两条只对内部运行成立，外部跟踪项不得复用；后者不依赖 Attempt |
| 计数 | `count_attempts` 只数 `attempts` 表 | 外部记录本就不该进 `attempts`，现有计数语义天然正确，无需改 |
| UI | `apps/workbench` 只有 `connection.ts` / `main.ts` / `connection.test.ts`，无 attempt/run/acceptance 引用；`apps/desktop` 无相关查询 | 没有 UI 在强制「必须来自内部运行」 |
| 发送意图 | `outbox_deliveries.status` 已含 `unknown`，主键 `(event_or_command_id, destination_id)`，以 `queue_key` 关联 `work_queue`（该表无外键） | 可复用登记发送意图；`work_queue` 是通用持久队列，不是内部运行，建一条队列不算造假 |

**结论**：走「增量迁移 + 显式关联表」，不新增外键、不改既有列。
新增迁移只放跟踪项/来源身份/目标关联/草稿四类表，内部引用列全部可空；
制品与证据复用 005 的三张表；发送意图复用 002 的 `outbox_deliveries`。
旧运行可追溯性不受影响：既有表和查询一行未改，回归靠现有 1280+ 用例兜住。

### 步骤

1. ~~盘点（只读）~~：见上（2.1）。
2. 路径冻结：6 个端点进路由表 + 重生成 `verification/openapi.json`（2.2）。
3. 读路径：跟踪项与覆盖结论（可查询、不写入）。
4. 写路径：导入、关联、补证入现有 Company 单写事务；落点为新增表，不复用 `acceptances`。
5. 草稿与发送：保存 → 重审 → 发送（复用 `outbox_deliveries`）→ 对账。

每步独立可回滚；第 2 步之后路径不能再改，实现顺序可以改。

### 3.1 落地时定下的五点

1. **库里不存覆盖结论**。表里只有事实（观察、开关、人群、验收条件），结论在读取时由
   `judge_coverage` 算出。存一份结论就一定会与事实漂移，而漂移后没人知道该信哪个。
2. **制品摘要取「最近一条带摘要的观察」**，不只认部署观察：离线安装回执引用的是同一个包，
   只认部署会让离线安装永久停在待核实——那不是更严格，是把合法交付判死。
3. **不做摘要冲突判定**。「同一版本出现两个摘要」是冲突，「新版本部署」也会换摘要；
   两者要靠来源身份与版本区分（3.2 / 3.5）。当前按时间取最新，并在报告里登记这个缺口，
   不假装已经处理。
4. **读路径先进 CLI（`bod tracking`），不先开 GET**。GET 的契约承诺「按调用者授权目标过滤
   对客户不可见的目标」，而 §34.12 的主体判定未实现；现在开放等于把不该给的客户给出去。
   CLI 是同一台机器上的操作者视图，不涉及跨主体过滤。
5. **新表之间用复合外键**（公司 + 跟踪项 + 目标），只约束本迁移新建的表。2.1 的
   「不新增外键」指的是不得为外部记录新增指向内部运行的外键；表内归属一致性用数据库拦，
   比只在应用层约定强。

### 3.2 落地时定下的六点

1. **迁移脚本必须天然幂等，所以观察与来源修订用关联表**。`SqliteStore::open` 每次打开都会
   重放全部迁移脚本（不是只跑未应用的），16 个既有脚本靠 `CREATE TABLE/INDEX/TRIGGER IF NOT EXISTS`
   保证重放安全。`ALTER TABLE ADD COLUMN` 没有 `IF NOT EXISTS`，给 016 的观察表加列会让
   第二次打开直接报 duplicate column。加列不是不能做，但要先改迁移机制，而机制一改，
   16 个脚本的「重放安全」假设全要重新论证——不划算。`delivery_observation_sources`
   顺带保证了「一条观察最多一条来源修订」。
2. **内容指纹不含观察时间**。指纹 = `(version, digest)`，所以重复上报同一事件命中同一行；
   含时间的话，每次上报都是新指纹，「同一重复事件只确认一次」就不成立。反过来，
   **同一标签两个摘要**指纹不同，两条修订都留着——这正是 §11「可变标签」要求的「不覆盖前一次观察」。
3. **「有稳定 ID 却没给对象类型」报错，不降级成候选**。降级看起来宽容，实际是让漏传字段
   静默停在待确认里，而且不报错。只有「根本没有稳定 ID」和「ID 字段里填的是 URL」才进候选。
4. **对象类型不做白名单，但强制 kebab-case**。连接器种类会持续增加，白名单会让新增连接器
   必须先改代码；但 `PullRequest` 与 `pull-request` 若都能落库，同一对象会变成两个身份。
5. **候选确认自带 `SAVEPOINT`**。它是一次动作两个写入（登记身份 + 改候选状态），
   若「身份写进去、状态没改」却返回失败，调用方很容易照样提交，于是同一 URL 留下两条待办。
   函数自己保证原子性，不依赖调用方记得回滚。
6. **主键仍由调用方给**（与 3.1 一致），ID 生成留给 3.5 的导入路径。理由同 3.1：
   测试要能确定地引用同一行；生成策略与幂等键是否复用同一个 ID，属导入语义。

### 3.3 落地时定下的五点

1. **键的作用域是 `(company, key)`，不含命令**。常见做法是按端点分作用域，那样「一个键用在
   两条命令上」会各建一条回执、各自重放，客户端拿到两个都「正确」的答案。这不是宽容，是替它
   猜意图：同一个键发两条不同命令本身就是缺陷，应当报出来。回执里存命令域，换命令报
   `IDEMPOTENCY_KEY_REUSED_FOR_OTHER_COMMAND`，与「换载荷」分成两档错误——合成一档的话，
   调用方会去改载荷，改完还是冲突。
2. **载荷指纹由内容派生，不含幂等键**。含了键，换键就等于换载荷，「同键异载荷」永远撞不上，
   本模块要拦的事正好被放过去。派生方式：字段按 `BTreeMap` 排序 → `serde_json` 编码 →
   sha256（`Digest::of_bytes`）。不做 trim：`"p1 "` 与 `"p1"` 是两个载荷，静默合并就是把
   一个打错的请求当成另一个的重放。
3. **回执与业务写入同事务**，且整段包在 `SAVEPOINT` 里。先写回执再干活，失败后重试会撞上
   自己伪造的冲突；先干活再写回执却不回滚，重试会重放出一个从未发生的成功。用例
   `failed_import_does_not_poison_the_key` 专门钉这条：缺对象类型失败后，同键重试必须仍是首次执行。
4. **重放返回首次执行的结果，不是今天的状态**。回执存 `result_detail`（首次响应的规范 JSON）：
   跟踪项可能已关闭、来源可能已补了修订，按现状重算会让「重放」变成第二个不同的答案。
   `created_*` 描述首次执行建了什么，`replayed=true` 说明本次没写入——两者不矛盾。
5. **对象去重落在关系表，而不是再加一层身份唯一性**。`delivery_tracking_sources` 主键
   `(company, source_id)`：一个来源身份只承载一条跟踪关系。重复导入返回它（`created_tracking=false`），
   换一条跟踪项挂则报 `SOURCE_ALREADY_LINKED`。不「改挂」：改挂是悄悄挪走一条已经承诺出去的交付。
   若将来要同一个 PR 支撑两个交付承诺，该改的是关系模型（多对多 + 显式意图），不是放宽唯一性——
   放宽之后「返回已有关系」就没有唯一对象可返回。

### 3.4 落地时定下的六点

1. **目标不加新表**。`delivery_targets`（016）的身份唯一索引
   `(company_id, tracking_id, customer_id, environment, deployment_unit)` 本身就是去重键：
   追加目标 = 按身份找，找不到才插入。再加一张「目标关联表」会让「这个客户交付到哪」
   有两个来源，一旦不一致就要两份记录各说一套。
2. **内部工作包单独成表**。`delivery_tracking` 上的 `issue_uid` / `run_uid` / `attempt_id`
   是三根单值列，表达不了「先后补入两个工作包修订」。工作包修订是一串事实，不是跟踪项的属性，
   所以 `delivery_tracking_work_packages` 以 `(company, tracking, revision)` 为主键。
   关联**不原地改写**（trigger 拒绝 UPDATE）：把已挂的修订改成另一个，等于伪造「谁在什么时候
   挂的哪一版」；挂错了应当删掉重挂。
3. **纯重复不推进版本**。关系和目标都已存在时 `appended=false`、`resource_version` 不动。
   若照样 +1，两个客户端会互相把对方的 `expected_version` 判过期，重试变成必冲突——
   「重试不重复建项」就成了空话。只有真的新增（新关系或新目标）才 +1。
   顺带一条：**重放返回首次执行后的版本**，不按今天的版本重算。客户端拿旧版本继续追加会得到
   409 而不是静默覆盖，失败在安全的一侧。
4. **期望版本不一致就什么都不写**。不做事后合并：那次写入是照着另一个状态做的决定，
   合并进去等于替调用方改主意。冲突里带当前版本，客户端不必再读一次。
5. **关系 ID 与目标 ID 由身份派生，不落库**。关系的身份就是（公司, 种类, 跟踪项, 引用），
   目标的是（公司, 跟踪项, 客户, 环境, 单元）。派生而不是字符串拼接：四段里的分隔符
   无法伪造出同一个 ID（分段先按长度前缀编码再求 sha256）。派生还让重试天然落到同一行。
6. **目标身份不 trim，但 `None` 与 `Some("")` 是同一个目标**。前者是因为 `"prod "` 与 `"prod"`
   是两条客户记录，静默合并等于把两条压成一条；后者是同一个事实的两种写法——存储层用空串
   表示「整个环境」（SQLite 唯一索引里 NULL 互不相等），入口不该留两种写法。

另有一条与视图对齐的硬约束：**已关闭的跟踪项不再接受关联**。`allowed_actions` 在关闭时
本来就不给 `link-source`，写入口若还放行，视图与事实就分家了。

**共享来源不合并客户记录**在模型里的答案是**一条跟踪项 + 多个目标**，不是多条跟踪项
（018 的主键决定一个来源身份只承载一条跟踪关系）。所以「不合并」必须落在目标这一层：
客户 A 的部署观察不得改变客户 B 的结论，也不得出现在它的证据里；用例
`shared_source_keeps_each_customer_record_separate` 钉的是这一条。

### 3.5 落地时定下的四点（审计接线）

1. **审计的动作词表与授权的动作词表分开**。`audit_events.action` 一直复用
   `authorization::StageAction`，而阶段动作每个变体都必须能回答「需要什么凭据」
   （`StageRequirement`）。导入与追加关联不属于任何阶段，硬塞进去只有两个结果：
   给它们编一个假的阶段要求，或者这些写入永远进不了审计。所以新增 `AuditAction`
   作为独立闭集，`From<StageAction>` 是唯一方向的映射——审计知道阶段动作，
   阶段判定不知道审计动作。这也正是 ADR-0007「不扩 `StageAction`」的直接后果。
2. **两个构造入口各挡错的那一类动作**。`AuditEvent::from_stage` 只产出阶段动作，
   `AuditEvent::for_write` 只产出业务写入，互相喂错返回
   `AuditRejection::ActionKindMismatch`。合并成一个构造函数的话，库里
   「准入被拒」与「写入成功」会长得一样，`decision=denied` 那条链就失去意义。
3. **`correlation_id` 由命令携带，不拿幂等键顶替**。第一版实现直接用幂等键当关联 ID，
   用例 `import_rolls_back_when_the_audit_row_is_refused` 当场撞出问题：测试用了键名
   `k-secret`，而脱敏闸门的 `SECRET_MARKERS` 含 `secret`，于是整条导入被判成
   「审计含凭据」而失败——键名决定成败，且失败点离病因很远。关联 ID 属于入口层
   （HTTP 请求 ID / CLI 会话 ID），与键的取值无关。
4. **审计与业务写入同事务，且只记真发生的事**。审计行写在同一个 `SAVEPOINT` 里，
   审计写不进去就整条回滚（四张表一起归零）；重放命中回执时**不写**审计，
   `appended=false` 的幂等空操作也**不写**——审计要回答「谁改了什么」，
   多记一条就等于凭空多出一次改动。

### 3.6 尚未落地：为什么工作量在接线（ADR-0007）

`authorization` 里 `filter_records` / `access_record` / `check_subscription` 都写好了，
但生产零调用，`StageFacts` 的四处构造全在测试里，也没有任何函数把 grants / members /
customer_bindings 从库里读出来。所以 3.6 的工作量在**装配端口**与 `Principal` 传参，
不在重写判定；先做 GET 是关键——写端点先上、过滤后补，等于把「没有过滤」发布成「已过滤」。

**已完成的一半（B1/B2/B6）**：`020_stage_facts.sql` 补了四张表（项目成员 / 客户绑定 /
发布操作人 / 撤权修订），`store::facts::StageFactsPort` 负责按主体装配六组事实。
四个决定值得留在设计里：

1. **成员分两层**。`members`(001) 是 Company 级身份，`project_members` 才是「在项目里有立场」。
   把 `project_id` 塞进 `members` 会让「同一个人换项目」变成两行同 uid 的冲突。
2. **一个主体只绑定一个客户**（主键决定）。`customer_of` 只返回一个答案，一对多会让判定
   依赖行序；需要多客户视角时用不同主体——客户是交付目标维度，不是数据所有权边界。
3. **撤权修订单独登记**，不从 `grants.active = 0` 反推：`grants.revision` 是授予时的修订，
   停用不 bump，反推会偏旧，而 `check_subscription` 用 `since < revoked_at` 决定重同步，
   偏旧等于漏一次重同步。这张表目前**没有写入者**（撤权命令尚未实现），
   所以 `revoked_at_revision` 仍是 `None`——这是现状，不是已实现。
4. **`assignments` 不建表**，从 `issues` 的 owner 三列派生。再建一张表就是第二份会漂移的
   真相，而且没有写入者。

剩下的是 B3（`Principal` 从哪来）/ B4（装配失败的对外映射）/ B5（GET 转 `served`），
三者都压在「主体来源」这一个决定上。

## 支持范围与已知限制（7.6.3）

这张表回答「**今天这一版**支持什么」，不回答「以后会支持什么」。每一行都必须可机械核对
（有测试或命令输出）；写「支持」而没有证据的项不应出现在这里。

更该说清楚——B 缩小了写者面，没有消除并发写。
