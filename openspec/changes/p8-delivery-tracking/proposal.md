# Proposal: P8 双入口交付与编码现场

## Why

P4 把候选交付推进到「实际环境 + 客户回执」，但它假定交付的对象是**内部研发产生的工作包**：
Run、Attempt、审批链都在宿主里。V2.9.8 §11 把这个假设打破了——真实的客户交付里，
相当比例的工作是**外部完成**的：一个已合并的 PR、供应商给的安装包、同事在别的系统里做的修复。
这类交付没有内部 Attempt，也不该为了记录它而伪造一个。

于是出现两个必须一起解决的问题：

1. **没有内部运行也要能记录交付承诺**。最小业务单位是「一项需求或变更在一个客户目标上的交付承诺」，
   它可以只由项目、来源关联、目标与回执表达。若 schema 强制内部 Attempt 外键，这类交付只能
   被塞进假工作包——那等于在权威记录里写假数据。
2. **两条入口必须给出同一个结论**。外部导入和内部研发描述同一组证据时，覆盖判定不能因为
   「没有内部运行」而降低或提高证据等级。这意味着覆盖投影必须是**共用的**，而不是两套代码
   各算一遍。

规格 §11 已经写明「路径在 OpenAPI 冻结时定稿」，所以本 Change 的前置是 CR-004 已完成
（`verification/openapi.json` 已入库、路由表即契约表，见 ADR-0004）。

## What Changes

- 定义**跟踪项**：需求/变更 × 客户目标的交付承诺，带验收条件、负责人与缺口清单；
  外部完成时内部 Run/Attempt/审批可缺省。
- 定义**来源身份**：Company + Project + 连接实例 + 来源对象类型 + 提供方稳定对象 ID 五元组；
  幂等键处理命令重放，身份约束处理「不同请求导入同一对象」；内容更新追加来源修订。
- 定义**目标与关联**：一个来源可关联多个构建、多个环境、多个目标；共享来源不合并不同客户的记录。
- 复用**共用覆盖投影**（`bod-app::coverage_receipt::judge_coverage`）：两条入口喂同一组
  规范化证据，得出同一结论。
- 定义**草稿**：保存目标、收件范围、证据修订、引用、缺口与文本修订；保存或生成草稿**不触发外发**。
- 定义**发送**：命令点与出站工作者各自重验授权、证据修订、目标与账号；证据变化则旧草稿进待重审。
- 定义**观测入站**：部署、回滚与人工补证按来源序列处理乱序，回滚追加纠正记录并关联原答复。

非目标：
- 不建第二个业务库、不建第二业务写入者（§5 单写事务不变）。
- 不做外部渠道 SDK 的通用抽象层，只为第一条真实通道写适配（P6 再谈开放扩展）。
- 不实现 AI 提取/起草的模型调用本身：无模型时必须能给出相同结论的规则摘要与人工编辑入口。

## Capabilities

### New Capabilities

- `delivery-tracking`：跟踪项、来源身份与修订、目标关联、外部导入的幂等与冲突、共用覆盖投影。
- `delivery-draft`：草稿装配、保存不外发、双点重验的发送、回滚纠正与发送未知的对账。

### Modified Capabilities

无。`coverage-receipt`（P4）只被**复用**，其 requirement 不改写；若实施中发现需要改，
按 openspec 的 MODIFIED 流程单独提出，不夹带在本 Change 的新增条目里。

## Impact

- 代码（预计）：`crates/bod-app/src/delivery_tracking/`（跟踪项、来源身份、目标关联）、
  `crates/bod-app/src/delivery_draft/`（草稿与发送重验）、`crates/bod-app/src/host_handshake.rs`
  （§11 的 6 个端点进 `ROUTES` 并声明 `contract`）。
- 数据：新增表需要通过**真实旧库**验证迁移（旧运行仍可追溯、外部记录可无运行、重复导入无重复回执）。
  是否物理迁移由仓库盘点决定，本提案不预设结论。
- 门禁：I-72（两条入口同一结论）由 planned 起，首切片接入后补跨入口用例；6 个端点的路径在
  `verification/openapi.json` 冻结后不再改动。
- 风险：若现有 DAO 强制内部 Attempt 外键，需要按 §33.7 做增量迁移或显式关联表——
  这属实施期发现，必须先盘点再动手，不允许「先塞个假 Attempt 顶上」。
